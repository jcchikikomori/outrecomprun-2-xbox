# Continuous Integration and Delivery

The CI workflow lives in `.github/workflows/ci.yml` and is named **CI**. It validates every push
and pull request on GitHub-hosted runners, builds the code-free recompiler tools on GitHub-hosted
runners, and builds the game executable on the maintainer's self-hosted Steam Deck runner, because
that machine is the only one with the user's own `default.xbe`.

The design follows one rule: **anything that reads or links game code runs on the maintainer's
machine; anything that does not runs on GitHub**. The compiled executable is published only when the
maintainer explicitly opens the publish gate.

## 1. Triggers

| Event | Details |
| --- | --- |
| `push` | `main`, `develop`, `feature/**`, `bugfix/**`, `hotfix/**`, and tags matching `v*` |
| `pull_request` | targeting `main` or `develop` |
| `workflow_dispatch` | optional `publish` boolean input, default `false` |

The `feature/**` form includes nested names such as `feature/audio/mixer`. Tag pushes are included
so that the `release` job in section 2 can run; without a tag trigger the job would never execute.

`concurrency` groups runs by workflow and ref. Runs are **not** cancelled when a newer push
arrives: the self-hosted runner removes its temporary directory when a job ends, and a cancelled
job that is still cleaning up deletes the temp directory of the next job, which then fails its
checkout with `could not lock config file .../_temp/<id>/.gitconfig: No such file or directory`. The
`build` job also recreates `$RUNNER_TEMP` before the checkout, so a stray cleanup cannot break it.
Workflow-level permissions are `contents: read`; only the release job raises them.

## 2. Jobs

| Job | Runner | Timeout | Role |
| --- | --- | --- | --- |
| `validate` | `ubuntu-latest` | 15 min | Static checks that need no game media |
| `tools` | `ubuntu-latest` | 45 min | Build `xbe_symbols` and `xbe_recomp` (code-free) |
| `build` | self-hosted Deck | 240 min | Stage the XBE, recompile, cross-build `Game.exe` |
| `release` | `ubuntu-latest` | 10 min | Draft a GitHub release on a `v*` tag |

`build` runs after `validate` and is skipped for pull requests from forks. `release` runs only when
the ref is a `v*` tag and the build succeeded.

### 2.1 `validate`

1. `bash -n` over `scripts/*.sh` and `scripts/ci/*.sh`.
2. TOML and JSON parsing for `config/outrun2.toml` and `CMakePresets.json`. `config/game.toml` is
   generated by `xbe_symbols` and untracked, so it is only parsed when present.
3. A tracked-file audit: no path under `assets/`, `generated/`, `out/` or `.local/`, and no tracked
   `.iso`, `.xbe`, `.cvm`, `.exe`, `.dll`, `.sav` or `.dmp` file. The same step asserts that
   `.gitignore` still contains `/assets/`, `/generated/`, `/out/`, `/.local/`, `*.iso` and `*.xbe`.
4. `git diff --check` over the pushed range when a base commit is available, plus a conflict-marker
   scan of tracked files.
5. Submodule pin check: `HEAD:sdk` must be
   `b908ae7f05908ff335f94037c673e4b437c7c1d6`, `.gitmodules` must point at the `hk21x` fork, and
   `sdk/cmake/XbeRecomp.cmake` must exist.
6. `DRY_RUN=1 scripts/cross-build.sh` and `DRY_RUN=1 scripts/container.sh harness 5`.
7. Markdown sanity: no heading-level skips and balanced code fences in tracked `.md` files.
8. The whole log is uploaded as `ci-validate-logs-<run_number>` with `if: always()`.

The two dry runs only print the container command. `scripts/cross-build.sh` checks for
`assets/default.xbe` before honouring `DRY_RUN`, so the preflight creates a **zero-byte placeholder**
when the checkout has no user media. It is never read by the dry run, never uploaded, and removed by
an `EXIT` trap. No game image is required on GitHub-hosted runners.

### 2.2 `tools`

`scripts/container.sh tools` builds the Docker image `outrun2-xbe-tools:24.04` from
`scripts/container/Dockerfile`, then compiles `xbe_symbols` and `xbe_recomp`. Those tools *read* an
XBE but contain no game code, so this job is safe on GitHub-hosted runners. The two binaries are
uploaded as `xbe-tools-linux-<sha>` with 14-day retention.

The shared SDK script only checks that `assets/default.xbe` exists; it never reads it while
building the tools. `scripts/ci/with-placeholder-xbe.sh` creates an empty placeholder for the
duration of the build and removes it afterwards, so the job needs no game media.

If the image build proves unreliable on GitHub (network or permissions), set the repository variable
`CI_TOOLS_NONFATAL` to `true`. The step then has `continue-on-error: true`, the job stays green, and
the job summary reports that the tools did not build. This is the only escape hatch: by default a
failure is red on purpose, so it cannot disappear silently.

### 2.3 `build`

Runs on the labels in the `RUNNER_LABELS` repository variable, defaulting to
`self-hosted,linux,outrun2-recomp`. Steps:

1. Check out with submodules. `clean: false` keeps `.local/xwin`, `build/` and `out/` between runs,
   because the Windows SDK sysroot is a large download.
2. Read `OUTRUN2_XBE_PATH`, copy the file to `assets/default.xbe`, and verify it with
   `( cd assets && sha1sum -c ../config/default.xbe.sha1 )`. This is why the checksum file names
   `default.xbe`: it is checked from inside `assets/`. An unset variable, a missing file or a
   checksum mismatch fails with a clear annotation.
3. Delete the previous `Game.exe` and this run's logs, so a failed build can never leave a stale
   executable for the collect step.
4. `scripts/container.sh tools`, then `symbols` (rewrites `config/game.toml`), then `recompile`
   (regenerates `generated/game`).
5. `RECOMPILE=1 scripts/cross-build.sh` with `JOBS` from `CI_JOBS` (default `3`).
6. Copy `out/build/cross-windows/Game.exe` to staging, and write `metadata.txt` with the commit,
   run URL, runner, size, SHA-256, pinned XBE SHA-1, build time and `file(1)` output. `logs/*.log`
   are copied when present. A failure path still uploads whatever logs exist. Staging lives in
   `.local/ci-staging`, which `.gitignore` already excludes.
7. Evaluate the publish gate and upload artifacts as described in section 3.
8. Write a job summary with the SHA-256, size and publish decision.

The build job is guarded with
`if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository`.
A public repository can receive a pull request from a fork whose branch edits `scripts/*.sh`; without
this guard that code would execute on the maintainer's machine. Fork pull requests therefore stop at
`validate`.

### 2.4 `release`

On a `v*` tag, after `build` succeeds, the job downloads `OutRun2-Windows-x64-*` and
`ci-build-logs-*`, writes notes, and creates a **draft** release with
`gh release create --draft --verify-tag --notes-file`. `Game.exe` is attached only when it was
published; `metadata.txt` is attached when available. If the artifacts are missing the download
steps continue on error, the job emits a warning, and the draft still carries the copyright notice
and a note that no executable was published. Re-running the job for an existing tag uploads assets
with `--clobber` and updates the notes instead of failing.

Draft means the release is invisible to the public until the maintainer reviews it and presses
publish. The tag itself is created by the maintainer, for example:

```bash
git tag v0.1.0
git push origin v0.1.0
```

## 3. The publish gate

`Game.exe` contains recompiled game code. The build job uploads it **only** when the repository
variable `PUBLISH_GAME_ARTIFACT` is `true`, or when a manual run sets `publish: true`.

| Trigger | `PUBLISH_GAME_ARTIFACT` | `publish` input | Executable uploaded |
| --- | --- | --- | --- |
| push to `main` | unset or `false` | not applicable | no |
| push to `main` | `true` | not applicable | yes |
| `workflow_dispatch` | unset or `false` | `true` | yes |
| `workflow_dispatch` | unset or `false` | `false` | no |
| `workflow_dispatch` | `true` | `false` | yes |

The last row is deliberate: the two sources are combined with OR, so the repository variable cannot
be vetoed by a manual run. A same-repository pull request also honours `true`, which is another
reason to keep the variable off outside release work. Fork pull requests never reach `build`.

When the gate is closed, the job uploads `metadata.txt` and logs only, and prints a notice in the
summary. The default state of a public repository never contains a redistributed executable.

## 4. Artifacts

| Artifact | Contents | Retention | Gate |
| --- | --- | --- | --- |
| `ci-validate-logs-<run_number>` | validation log | 7 days | always |
| `xbe-tools-linux-<sha>` | `xbe_symbols`, `xbe_recomp` | 14 days | tools built |
| `ci-build-logs-<run_number>` | `metadata.txt`, `logs/` | 7 days | always |
| `OutRun2-Windows-x64-<sha256[0:12]>` | `Game.exe` | 14 days | publish gate open |
| draft release `v*` | `Game.exe` when published, `metadata.txt` | permanent | publish gate open |

**Artifacts of a public repository are public.** Anyone who can read the repository can download an
artifact while it exists, and a published release stays downloadable. Setting
`PUBLISH_GAME_ARTIFACT=true` is therefore a distribution decision, not a private convenience.

A player who downloads the executable still needs:

- their own legally acquired *OutRun 2* disc (or an extracted `assets/` folder), because the
  executable contains no game media;
- the Microsoft Visual C++ 2015-2022 x64 runtime under Wine or Proton;
- a GPU/driver stack that provides Direct3D 12 through vkd3d-proton.

## 5. Repository variables

Set them in **Settings → Secrets and variables → Actions → Variables**. None of them is a secret;
repository variables are visible to anyone who can read the repository, and a self-hosted path is
not sensitive. Never put the XBE itself in a secret: it is 3.1 MB, well above the 48 KB secret limit,
and it must not leave the machine.

| Variable | Required | Example | Meaning |
| --- | --- | --- | --- |
| `OUTRUN2_XBE_PATH` | yes, for `build` | `/home/deck/.local/share/outrun2-recomp/default.xbe` | absolute path to the local `default.xbe` |
| `RUNNER_LABELS` | no | `["self-hosted","linux","outrun2-recomp"]` | JSON label array for `runs-on` |
| `PUBLISH_GAME_ARTIFACT` | no | `true` | publish `Game.exe`; default off |
| `CI_JOBS` | no | `4` | ninja parallelism for the cross-build, default `3` |
| `CI_TOOLS_NONFATAL` | no | `true` | make a `tools` failure non-fatal; default off |

`gh` equivalents:

```bash
gh variable set OUTRUN2_XBE_PATH --body /home/deck/.local/share/outrun2-recomp/default.xbe
gh variable set RUNNER_LABELS --body '["self-hosted","linux","outrun2-recomp"]'
gh variable set PUBLISH_GAME_ARTIFACT --body true
gh variable delete PUBLISH_GAME_ARTIFACT
```

## 6. Self-hosted runner setup (one time)

The runner needs the game image, a container engine and enough disk for the xwin sysroot and two
container images. Do this on the Deck while it is idle.

### 6.1 The scripted way (what this machine uses)

```bash
scripts/ci/setup-runner.sh
```

The script registers the machine with the repository through the GitHub API (it needs `gh`
authenticated for it), unpacks the runner into `~/.actions-runner`, installs it as the **user**
service `actions-runner.service` and starts it. No root is needed: the service lives in
`~/.config/systemd/user/` and `loginctl enable-linger` keeps it running when nobody is logged in.

Keep the game image outside any checkout, so a checkout can never overwrite it:

```bash
mkdir -p ~/.local/share/outrun2-recomp
cp /path/to/your/default.xbe ~/.local/share/outrun2-recomp/default.xbe
gh variable set OUTRUN2_XBE_PATH --body "$HOME/.local/share/outrun2-recomp/default.xbe"
```

Useful variations:

```bash
scripts/ci/setup-runner.sh --no-service   # register and run in the foreground
scripts/ci/setup-runner.sh --remove       # unregister the runner and stop the service
systemctl --user status actions-runner    # is it running?
```

> **Run exactly one runner instance for this work directory.** Two listeners sharing
> `_work/` clean each other's job directories: the first job to finish wipes `_work/_temp`
> while the other is still running, and that job fails with
> `could not lock config file .../_temp/<id>/.gitconfig: No such file or directory`. The
> systemd service is the single instance; do not also start `run.sh` by hand.

### 6.2 The manual way

1. Open the repository on GitHub, then **Settings → Actions → Runners → New self-hosted runner**.
   Download the Linux x64 runner and copy the URL and token that page shows.
2. Configure it with the labels this workflow expects:

   ```bash
   mkdir -p ~/actions-runner-outrun2
   cd ~/actions-runner-outrun2
   # unpack the runner tarball shown on the GitHub page
   ./config.sh --url <repository-url> --token <registration-token> \
       --name deck-outrun2 --labels self-hosted,linux,outrun2-recomp \
       --work _work
   ```

3. Install it as a user service so it starts with the session and survives a reboot:

   ```bash
   sudo ./svc.sh install "$USER"
   sudo ./svc.sh start
   sudo ./svc.sh status
   ```

4. Check that the container engine works for the account that runs the service:

   ```bash
   docker info     # or: podman info
   ```

   The repository's scripts pick Docker when it exists and Podman otherwise, and they detect a
   Podman shim named `docker`. A rootless Podman install needs no group membership, so on
   SteamOS there is usually nothing to change.

5. Point `OUTRUN2_XBE_PATH` at the local `default.xbe` (section 5). The workflow copies it into
   `assets/default.xbe` in the runner's workspace; the copy is git-ignored and never uploaded.

### 6.1 Security notes for a public repository

- The runner is **inbound only**: it polls GitHub over outbound HTTPS. Do not forward or open ports
  for it, and do not expose it as a general-purpose build service.
- GitHub explicitly warns that a self-hosted runner on a public repository can be made to execute
  code from workflows and pull requests. This workflow blocks fork pull requests from the `build`
  job, but **the machine must be dedicated to this repository**. Do not register it against other
  repositories, and do not keep unrelated credentials or personal data on the account.
- Prefer the default branch protection and the "Require approval for fork pull request workflows"
  setting. Treat any new workflow file as a review gate: a workflow change can change what runs on
  the Deck.
- Do not store secrets on this runner beyond what the job needs. The build uses no secrets at all.
- The account that runs the service can read `assets/default.xbe` and the GitHub token that
  `actions/checkout` stores in the workspace. That token is short-lived and read-only for code.

## 7. Copyright boundary

- `default.xbe`, disc images, CVM archives and extracted media are user-owned game data. They are
  never committed, never uploaded, and never a GitHub secret.
- `generated/game` is recompiled game code. It is regenerated on the Deck and stays out of version
  control because `/generated/` is ignored.
- The default publishing policy distributes only metadata and logs. Enabling
  `PUBLISH_GAME_ARTIFACT` (or ticking `publish` on a manual run) is the maintainer's explicit
  decision to publish the compiled executable to a public artifact.
- *OutRun 2* is © SEGA. This project is not affiliated with or endorsed by SEGA. A published
  executable is a recompilation of the user's own game and is useless without that game.

## 8. Peer-project comparison

Every other XboxXBERecomp-based project keeps compiled game code off CI:

| Project | CI behaviour |
| --- | --- |
| `hk21x/pgr2-recomp` | `release.yml` builds a code-free launcher on `windows-2022`, uploads it as an Actions artifact, and creates a draft release on `v*` tags for the maintainer to complete |
| `TGP482/SCDA-XBERecomp` | ships a first-start compiler; the player builds the game on their own PC |
| `TGP482/XboxXBE-Recomp` | same first-start compiler model; no compiled game code in CI |
| `abilliontokens/fuzionfrenzy-recomp` | no compiled game code published by CI |
| `xenophobentx/takedawn` | no compiled game code published by CI |

This repository follows `pgr2-recomp` for the draft-release pattern and the code-free launcher
artifact, then deviates deliberately: it *can* publish the compiled game executable, but only behind
the explicit `PUBLISH_GAME_ARTIFACT` switch, and never on the default path. The maintainer alone
decides whether that switch is on, and the draft release keeps a second review gate before anything
becomes public.

## 9. Operating it

### 9.1 Disable or enable

```bash
gh workflow disable ci.yml     # stop all triggers
gh workflow enable ci.yml
```

To take the build offline without touching the workflow, stop the runner service
(`systemctl --user stop actions-runner`) or remove the `self-hosted` label. `validate` and
`tools` keep working on GitHub-hosted runners; `build` stays queued until the runner returns.

To publish for one run only, use **Actions → CI → Run workflow** and tick `publish`. To change the
default, set the repository variable and leave the runner to pick it up on the next run.

### 9.2 Re-run a failed job

Use the run page's **Re-run failed jobs** button, or:

```bash
gh run list --workflow ci.yml --limit 5
gh run rerun <run-id> --failed
gh run watch <run-id>
```

A re-run uses the same commit and the variables as they are **now**, not as they were at the first
attempt. A queued `build` needs the Deck runner online; the job does not fail just because the
runner is offline, it waits. Artifacts use fixed names and `overwrite: true`, so a re-run replaces
them instead of failing on a duplicate name.

### 9.3 Reproduce the validation locally

These are the same commands the `validate` job runs:

```bash
for f in scripts/*.sh scripts/ci/*.sh; do bash -n "$f"; done
scripts/ci/check-config.sh
scripts/ci/audit-tracked.sh
BASE_SHA=$(git rev-parse HEAD~1) scripts/ci/check-diff.sh
scripts/ci/check-submodule.sh
scripts/ci/dry-run-preflight.sh
scripts/ci/check-markdown.sh
```

The publish gate needs no container. It is the shell logic in the `Decide whether the executable may
be published` step and follows the truth table in section 3.

## 10. Known limitations and first-run risks

- **The Deck runner must be online.** A push to `main` queues `build`; `release` on a tag cannot run
  until `build` finishes. Start the service before tagging.
- **First run on a new machine is slow and network-heavy.** Docker builds two images, the tools
  container pulls Ubuntu packages, and the cross-build downloads `xwin` and splats the Windows SDK
  and UCRT into `.local/xwin`. Later runs reuse them because the build job checks out with
  `clean: false`.
- **Container engine permissions.** If the runner account cannot use the engine,
  `scripts/container.sh` fails with its own message and the build job stops at the tools step. On
  SteamOS, rootless Podman works without any group change; a rootful Docker install needs the
  account in the `docker` group.
- **State is kept between runs.** `clean: false` leaves `.local/xwin`, `build/`, `out/` and
  `generated/` in the workspace. The job deletes the previous `Game.exe` and logs and regenerates
  `generated/game` with `RECOMPILE=1`, but a corrupted build directory may need a manual
  `rm -rf out/build/cross-windows` on the Deck.
- **The checksum is region-specific.** The pinned SHA-1 is the European `default.xbe` used for all
  published evidence. Another dump fails the SHA-1 check before any recompilation.
- **Artifacts expire.** 7 and 14 days are intentional. A release is the only durable copy, and only
  when the gate was open.
- **No signing.** `Game.exe` is unsigned; Windows SmartScreen and some Wine configurations will
  complain.
- **Local changes are not preserved.** `assets/default.xbe` is overwritten from `OUTRUN2_XBE_PATH`
  on every run by design, so the build always uses the file the variable names.
